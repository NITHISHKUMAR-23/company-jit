Description

This OSPI driver test example illustrates the direct code execution (XiP) from flash using direct mode of OSPI controller. This example works standalone on EV-SC59x-SOM/EV-21593-SOM, as well as supported on both EV-SOMCRR-EZKIT and EV-SOMCRR-EZLITE.

Ideally, the XiP mode in a flash device improves the execution performace by eliminating the read command for every read while executing code from flash. Very first read command is essential initially along with specific mode bits to enable the XiP mode in flash (may vary flash to flash). In ISSI IS25LP512M XiP mode is entered by sending the 0xAX mode data during the dummy cycle phase (mode bits). The example operates in DIOR mode for sending address and reading data on 2 SPI lines.

The function "Code_In_Flash(uint32_t nIteration)" is mapped to flash space and this code is what is run form flash memory. So for executing from flash the binary opcodes for this this code, need to be programmed into the flash at address 0.

The example does following:

  1. Enables the access to ISSI Quad flash on board by configuring the soft config switch through TWI2.
  2. Configures the controller to do direct read transaction accesses in direct mode in Dual I/O mode.
  3. Issue a Dual I/O read to flash and sends the 0xAX pattern to flash during dummy cycle causing the flash to enter XiP mode.
  4. Configures the controller to enter XiP mode immediately on next read.
  5. Jumps to the code function placed in flash memory. The code is fetched form flash in XiP mode with read command sent just once.
  6. This function is called multiple with a different parameter passed each time. Each time the function does some mathematical operation and returns the results back which is then compared with the expected value.
  7. If all the function calls return correct values the example is declared passed.
  8. After all iterations are done, flash is taken out of XiP mode by issuing a read with non 0xAX mode data during dummy cycle phase .
  9. Controller is configured to exit the XiP mode.

The source code for this example is common to support three examples, SHARC core code execution for ADSP-21593 for EV-21593-SOM, SHARC core code execution for ADSP-SC594 for EV-SC594-SOM and arm core code execution for ADSP-SC594 for EV-SC593-SOM

For SHARC projects, post build script 'post-build.bat' placed in respective SH core1 folder of the project handles the extraction of flash opcodes from the executable using romsplitter option of elfloader.exe. The extracted opcodes (in hex file) are then programmed to flash using cldp. The path for the flash programmer as given in the .bat file needs to be updated as per your ADSP-SC594 BSP installation path. Since post build script is run after the project build is complete, above 2 steps are executed one after the other after project build is done. And after the script is executed, all the required opcodes are programmed into the flash at required address. After this loading the project and executing it will execute the code from flash as mention in above steps. 'post-build.bat' script needs to be added to Post-build steps under Build Steps tab C/C++ Build -> Settings in project properties

For arm project, post build script 'post-build.bat' placed in respective arm core0 folder of the project handles the extraction of flash opcodes from the executable using objcopy.exe. The extracted opcodes are extracted into a binary file 'ospi_xip_codeexec_SC594_Cortex_Core0.dat' which will be stored in Debug or Release folder depending on project configuration. For this to be done correctly, user has to make sure that the flash section defined in 'app2.ld' file under ..\ospi_xip_codeexecution\EV-SOMCRR-EZKIT\SC594\arm\ospi_xip_codeexec_SC594_Cortex_Core0\system\linker is defined as loadable (NOLOAD attribute should be removed) at line 245 (for SC594), line 238 (for SC598)

.ospi_flash_code :

After this the user has to flash these opcodes to the flash using the cldp and flash programmer. Script does not take care of that. After file contents are programmed into the flash at required address. After this is done user has to modify the .ld file again to make the flash section non-loadable by modifying line 245 to this:

.ospi_flash_code (NOLOAD):

This will make the flash section to be ignored from the final executable so that the debugger can load the executable to the processor while retaining the symbols to the code placed in flash. If the section is not defined as NOLOAD, emulator will try loading the flash section too and thus will fail in loading the executable. Once the project is build with NOLOAD attribute, the built project can be loaded and executing it will execute the code from flash as mention in above steps

@Note: ICE-2000 is used by default in the file "post-build.bat" by default. If any other ICE is used, then it should be re-configured for the ICE being used

@Note: In this example at the end of every build "post-build.bat" will program the flash device. So it is required to reset the board after every build and before run the example.

Overview

This OSPI driver test example illustrates the direct code execution (XiP) from flash using direct mode of OSPI controller.

Code Execution from Flash happened correctly" and "All Done" printed to the console signifies the code was executed from flash correctly

"Fail" printed to the console signifies that the test example has failed. Other errors are also printed if any of the driver operation fails in between and the code is terminated

Note: When running the example a warning would pop up on the console. This is an expected warning. It's basically saying that you need to flash the ROM sections as they can't be loaded by CCES. The example does take care of this by using cldp to write the needed SPI flash blocks. "Warning: section containing address 0x00F80000 is SPI memory and will be skipped during load, you must program SPI memory separately."

User Configuration Macros

  1. Disable both EV_SOMCRR_EZKIT_SUPPORT & EV_SOMCRR_EZLITE_SUPPORT in ospi_xip_codeexecution.h file to verify the example in EV-SC59x-SOM/EV-21593-SOM alone without connecting any CRR boards.
  2. Enable EV_SOMCRR_EZKIT_SUPPORT in ospi_xip_codeexecution.h file to verify the example on EV-SOMCRR-EZKIT.
  3. Enable EV_SOMCRR_EZLITE_SUPPORT in ospi_xip_codeexecution.h file to verify the example on EV-SOMCRR-EZLITE.

    4. Note 1: By default both EV_SOMCRR_EZKIT_SUPPORT & EV_SOMCRR_EZLITE_SUPPORT are disabled in ospi_xip_codeexecution.h.

    Note 2: By default EV_SOMCRR_EZKIT_SUPPORT is set as TargetSupport in post-build.bat. This should be updated based on the target carrier board.

Pinmuxing

The following pins are used for the OSPI operation:

  1. OSPI_CLK
  2. OSPI_MISO
  3. OSPI_MOSI
  4. OSPI_D2
  5. OSPI_D3
  6. OSPI_SEL1
