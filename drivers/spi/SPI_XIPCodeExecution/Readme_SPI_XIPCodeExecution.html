Description

This SPI example illustrates the direct code execution (XiP) from flash.

Ideally, the XiP is best done when flash is put in XiP mode and initially by sending read command only so that there is no need to send the read command subsequently. However, since ISSI IS25LP512M does not have support for XiP mode, the code execution is done without putting the flash in XiP mode This requires that the controller also should not to be in XiP mode so that the controller sends the read commands for each instruction fetch as expected by flash.

SHARC projects have post build script "post-build_21593.bat/post-build_SC594.bat/post-build_SC598" EZKIT/EZLITE placed in respective SH core1 folder of the project which handles the extraction of flash opcodes from the executable using romsplitter option of elfloader.exe. The extracted opcodes (in hex file) are then programmed to flash using cldp. The path for the flash programmer as given in the .bat file needs to be updated as per your ADSP-SC594 BSP installation path. Since post build script is run after the project build is complete, above 2 steps are executed one after the other after project build is done. After the script is executed, all the required opcodes are programmed into the flash at required address. 'post-build.bat' script needs to be added to Post-build steps under Build Steps tab C/C++ Build -> Settings in project properties This setting is configured in this particular example for reference. @Note: ICE-2000 is used by default in the file "post-build_21593.bat/post-build_SC594.bat/post-build_SC598" EZKIT/EZLITE by default. If any other ICE is used then it should be configured for the ICE being used

The example does following:

  1. Enables the access to ISSI Quad flash on board by configuring the soft config switch through TWI2.
  2. Configures the controller to do direct read transaction accesses in direct mode in standard SPI mode.
  3. Jumps to the code function placed in flash memory.
  4. If all the functional calls return correct value then the LED blink code gets executed to showcase the example.
  5. This example is supported both on EV-SOMCRR-EZKIT and EV-SOMCRR-EZLITE.

Overview

On successfully completion of the code execution from flash, an LED blink code is executed and the LEDs can be seen blinking on the SOM Carrier board

Note: When running the example a warning would pop up on the console. This is an expected warning. It's basically saying that you need to flash the ROM sections as they can't be loaded by CCES. The example does take care of this by using cldp to write the needed SPI flash blocks. "Warning: section containing address 0x00F80000 is SPI memory and will be skipped during load, you must program SPI memory separately."

User Configuration Macros

  • Enable EV_SOMCRR_EZKIT_SUPPORT in SPI_XIPCodeExecution.h file to verify the example on EV-SOMCRR-EZKIT
  • Enable EV_SOMCRR_EZLITE_SUPPORT in SPI_XIPCodeExecution.h file to verify the example on EV-SOMCRR-EZLITE

Pinmuxing

Following is the pinmux configuration:

  1. TWI2 (SCL, SDA)
  2. SPI2 (CLK, D2, D3, MISO, MOSI, RDY, SEL1)
  3. GPIO(unavailable) (PA00, PA01, PA02, PA03, PA04, PA05, PA14, PA15, PB05)
